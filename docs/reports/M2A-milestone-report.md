# M2A COMPLETION REPORT — Merge PDF Vertical Slice

Date: 2026-09-25

Status: Implementation complete; final verification, hosted CI and independent-viewer confirmation are being closed out. This report covers M2A only. M2B has not started and all of M2 is not complete.

## Implemented and architecture

Choose/add PDFs → validate → arrange selected files → merge locally → download a valid PDF → edit selection or start over. Duplicate selections retain distinct identities. Remove, Move earlier/later and native file selection work with keyboard controls; drag/drop is an additional input path. Processing has real phase text, prevents duplicate submission, and supports cancellation. Download is the primary success action.

The server route sends only serializable registry configuration and presentation. A route-local client session owns Files, order, errors, abort state and the current result URL. The lazy PDF package starts one native worker per operation, copies source pages sequentially through pdf-lib, validates the output, and returns a Blob. Reset, replacement and navigation release owned references and revoke URLs. No backend, processor, server action, persistence, analytics or third-party service handles documents. ADR-012 records the decisions; ADR-010 and the protected CI architecture remain unchanged.

## Worker evidence and limits

Initial async main-thread image workloads caused repeated long tasks under a page CPU throttle: 10 pages produced 191–284 ms timer delays; 50 pages produced 11–12 long tasks per repeat and delays up to 366 ms. This triggered the approved worker amendment. Worker runs recorded zero main-thread long tasks and permit immediate termination; no main-thread fallback is used.

The explored corpus covered 10/50/100/240 pages, 40 files and about 50.4 MiB of image-heavy inputs. Conservative engineering caps are **20 files, 10 MiB per file, 32 MiB combined, 200 pages, 32 MiB output**. Boundary runs passed 20 files/200 pages and six files/~30.2 MiB of images within those caps. Host scheduling varied: boundary completion ranged from 1.49 to 5.611 seconds and one timer-delay sample reached 469 ms despite no measured long task. CDP throttles the page thread, not worker CPU; these are not physical-mobile results or public performance guarantees. Full records and methodology are in `docs/benchmarks/M2A.md`.

## Corrections, deviations and remaining decisions

Corrected pdf-lib's ES5 encrypted-error prototype behavior with safe fixed-message mapping, isolated document-derived dependency warnings inside the worker, fixed the enlarged-text download layout, scoped browser alert locators around Next's separate announcer, and restored the About preview qualifier. No check was removed, skipped or disabled, and no timeout/retry policy was weakened.

No unapproved product or architecture deviation. The worker was added only after measured evidence triggered the approved condition. Forms/signatures remain accepted with tested limitations; PDF.js/thumbnails/Split/Organize/page controls are absent. Browser hardening remains the existing Chromium desktop/mobile baseline, as approved.

Remaining launch decisions include physical-mobile/broader-browser sizing, final public limits, broader PDF feature coverage, branding/legal policies and launch indexing/deployment. The engine does not sanitize documents, flatten forms, repair unsupported inputs, validate signatures or promise hard memory bounds. Main-thread scheduling can still vary with host load.

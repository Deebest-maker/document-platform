## 2. What the engine does

Phases, in order: `reading → removing → validating → verifying`.

1. **Reading.** Shared `readPageInput` validates size, mime, page count and output cap. `PDFDocument.load(bytes, { ignoreEncryption: false, updateMetadata: false })` reads the file. `EncryptedPDFError` is mapped to `ENCRYPTED_PDF`.
2. **Removing.** Snapshot `before` metadata flags. Delete every entry on the Info dictionary (both standard ISO 32000-1 §14.3.3 keys and any custom keys authoring tools added); detach `trailerInfo.Info`. Delete `Catalog /Metadata` (the XMP stream). Attempt `delete trailerInfo.ID` as the SPIKE step.
3. **Validating.** `save({ useObjectStreams: false })` produces the output. The byte count must be at least 32 and no more than `maxOutputBytes`.
4. **Verifying — structurally scoped in production.**
   - **pdf-lib reopen pass (the publication gate)**: load the saved bytes in a fresh `PDFDocument`, snapshot `after` metadata flags, compare page count and per-page `mediaBox` and rotation against the `before` snapshot. Every check is structurally scoped by pdf-lib's parser (it looks at the specific PDF object the field lives in), so none can false-positive on a lookalike byte sequence elsewhere. If any targeted field survived or geometry changed, throw `OUTPUT_INVALID` and publish nothing.
   - **Trailer /ID structural second opinion**: `scanTrailerIdStructural` reads a bounded slice of the saved bytes from the final `trailer` keyword to the following `startxref` and reports only `/ID` entries that live inside that slice. It is used solely to down-correct `trailerIdControllable` for the SPIKE — never to promote it, never to look at any other field, never to false-positive outside the trailer.
   - **Whole-body scan (TEST-ONLY, outside the engine)**: `scanWholeBody` lives in `packages/pdf-browser/tests/helpers/metadata-whole-body-scan.ts` and is NOT reachable from any production code path. The engine does not import it, does not call it, and does not attach it to the result. Tests invoke it on the engine's output as a bug detector; a global regex can false-positive on legitimately-placed byte sequences, so it would be wrong to use it as a publication gate.

The result reports both snapshots, the list of fields the engine removed, `trailerIdControllable` and the full `independentScan` result (so tests, benchmarks and the Product Owner can inspect the byte-level flags directly). The UI only claims trailer /ID removal when `trailerIdControllable && before.trailerIdPresent`.

## 3. Privacy budget

- No document bytes, extracted strings, filenames or canaries leave the browser. The E2E audit asserts this with every network request stored and inspected.
- The engine's result surface is **flags and key names only**. Raw string values (titles, author names) never cross the engine boundary.
- The session mirrors this: it carries counts and booleans, not strings.
- Benchmark output is schema-only on first commit. Non-zero `requestAudit.crossOrigin` or `requestAudit.canaryLeaks` fails the run.
- Four canary strings exercise the audit: `SECRET-TITLE-CANARY-9Hjk`, `SECRET-AUTHOR-CANARY-2Fqz`, `ACME-INTERNAL-CANARY-X3b`, `XMP-CANARY-V7m`.

## 4. Known limits (reported truthfully)

- **Trailer /ID is a SPIKE.** `trailerIdControllable: false` is a real possible outcome. The UI must say so when it happens; the ADR and the privacy page restate it.
- **Not secure redaction.** Text and images on each page, embedded files, incremental-update history, structure trees and anything inside page content streams are untouched. The route page says this before any file is selected.
- **Encrypted PDFs are refused** with error copy "This PDF is password-protected. Unlock it before removing metadata."
- Engineering caps per the catalog: 1 file, 10 MiB input, 200 pages, 32 MiB output.
